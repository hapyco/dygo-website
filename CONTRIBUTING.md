# Contributing

dygo.dev is open for contributions.

This repository is the public home for the official Dygo website. Contributions
that improve the website, documentation, examples, clarity, accessibility, and
developer experience are welcome.

The Dygo framework itself lives in a separate repository and is licensed
separately under the O'Saasy License. Framework behavior, CLI changes, runtime
changes, and core architecture changes should be discussed in the framework
repository, not here.

## What Helps

Good contributions for this repository include:

- fixing unclear wording
- improving documentation structure
- adding examples and guides
- correcting broken links or stale references
- improving accessibility
- improving responsive behavior
- tightening visual details
- improving performance and SEO
- improving the contributor experience

If a change would affect how Dygo itself works, open an issue first so we can
route it to the right place.

## Before Opening a Pull Request

For small fixes, a pull request is fine directly.

For larger changes, open an issue first and describe:

- what problem you are solving
- what page or workflow is affected
- what you plan to change
- any tradeoffs or open questions

This keeps review focused and avoids spending time on changes that do not fit
the website direction.

## Writing Guidelines

Write for developers who are deciding whether Dygo is the right framework for
serious business applications.

Prefer:

- direct explanations over vague claims
- concrete examples over slogans
- short pages with clear paths forward
- stable terminology that matches the framework docs
- honest limitations where the project is still evolving

Avoid:

- overstating what Dygo can do today
- introducing new framework concepts casually
- changing doctrine or positioning without discussion
- marketing copy that hides the technical idea
- copying content from other projects without permission and attribution

## Pull Request Guidelines

Keep pull requests focused. A small, complete change is easier to review than a
large mixed one.

Before opening a pull request:

- check spelling and formatting
- test the affected pages locally when the site has a runnable setup
- include screenshots for visual changes
- explain the user-facing effect of the change
- mention any follow-up work that should happen separately
