---
title: App model
description: Organize business metadata and compiled behavior in a dygo App.
---

An App is the deployment and ownership boundary for business behavior.

Apps live under `apps/<app>` in a generated project. Each App has a manifest and can own Entities, access policy, Fixtures, Hooks, Jobs, Schedules, and Patches.

## Create an App

```sh title="Terminal"
dygo generate app crm
```

The generator creates valid starter files. It does not overwrite custom files.

Preview the change first:

```sh title="Terminal"
dygo generate app crm --dry-run
```

## App directory

```text title="Project files"
apps/
└── crm/
    ├── app.yml
    ├── access/
    │   └── _roles.yml
    ├── entities/
    └── jobs/
        └── _schedules.yml
```

As the App grows, each Entity gets its own bundle:

```text title="Entity bundle"
apps/crm/entities/contact/
├── contact.entity.yml
├── fixtures.yml
├── hooks.go
└── hooks_test.go
```

## Manifest

`app.yml` identifies the App and its metadata directories. App identity comes from the manifest, not its display label.

Validate all discovered Apps:

```sh title="Terminal"
dygo app validate
```

List the Apps that dygo can see:

```sh title="Terminal"
dygo app list
```

## Ownership rule

Put business rules in the App that owns them. Use dygo for shared platform capability such as Record storage, permissions, background work, secrets, and Studio rendering.

App code must use the public packages under `pkg/dygo`. Framework implementation under `internal/` is not a stable App API.

## Built-in Apps

Core is the required system App. Studio is the first-party interface App. A generated project also contains its own business Apps.

Core and business Apps use the same metadata model where practical. Framework bootstrap can use narrow exceptions, but it must not create a private product capability that Apps cannot reach.

## Write a manifest

```yaml title="apps/crm/app.yml"
name: crm
label: CRM
version: 0.1.0
description: Customer relationship management
dependencies:
  - core
paths:
  entities: entities
  patches: patches
  docs: docs
  assets: assets
```

Name, label, and version are required. Paths are clean, relative App paths. Dependencies name installed Apps; manifest version constraints and remote source declarations are not supported. Framework-owned names such as `core`, `studio`, and `localization` are reserved.

## Install an existing App

Use the real repository URL of the App you want to install:

```sh title="Example repository URL"
dygo app install https://github.com/acme/dygo-crm.git --dry-run
```

The example URL is a placeholder. The repository root must contain `app.yml`, and its dependencies must already be installed. After review, remove `--dry-run` to copy App source without Git metadata and update Hook and Job runner wiring.

App installation changes project files only. Build or run the project runner, then use `go run ./cmd/dygo db migrate` to apply App state, Patches, metadata, access, and Fixtures with the App's compiled code. Apps may also own [Pages and compiled actions](/build-apps/actions-and-pages/).
