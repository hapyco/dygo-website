title: Entities
description: Define business Records, Fields, naming, links, collections, indexes, and constraints in YAML.
---

An Entity defines the structure of a business Record. dygo reads Entity YAML during validation and database migration. Studio and the generic Record API use the persisted metadata.

## Generate an Entity

```sh title="Terminal"
dygo generate entity crm/contact
```

The standard generator creates Entity metadata, access metadata, and a Fixture skeleton. Generate Hook code and tests separately with `dygo generate hook crm/contact` and `dygo generate test crm/contact`.

Skip parts that the Entity does not need:

```sh title="Terminal"
dygo generate entity crm/contact --no-access --no-fixture
```

## Define the metadata

Edit `apps/crm/entities/contact/contact.entity.yml`:

```yaml title="apps/crm/entities/contact/contact.entity.yml"
label: Contact
description: A person known to the CRM
icon: user
route:
  slug: contact
name:
  strategy: format
  format: "{email}"
fields:
  - name: full-name
    label: Full Name
    type: text
    required: true

  - name: email
    label: Email
    type: email
    required: true
    unique: true

  - name: status
    label: Status
    type: select
    index: true
    options:
      values:
        - Lead
        - Customer
        - Archived
```

Entity and Field keys use kebab-case. The parent directory defines Entity identity. The top-level `name` section defines Record naming.

## Record identity

Every Record has:

- `id`, the internal numeric primary key
- `name`, the stable system or business identifier
- `created-at`
- `updated-at`

Normal Entities require a `name` section and support `random`, `manual`, `format`, and `series` naming strategies. Use `name.strategy: random` when you do not need a business naming rule.

Use a series for ordered business identifiers:

```yaml title="invoice.entity.yml"
name:
  strategy: series
  pattern: "SINV-{YYYY}-{MM}-{#####}"
```

Changing a Field used by `format` naming does not rename an existing Record.

## Links

A `link` Field points to a Record from another Entity:

```yaml title="invoice.entity.yml"
fields:
  - name: customer
    label: Customer
    type: link
    required: true
    options:
      entity: customer
```

Set `options.app` for a cross-App link or an ambiguous Entity key.

## Collections

Collections store parent-owned rows such as invoice items. Define collection metadata under `entities/_collections/` and reference it from the parent:

```yaml title="invoice.entity.yml"
fields:
  - name: items
    label: Items
    type: collection
    options:
      entity: invoice-item
```

Collection rows are not routeable Records. dygo deletes them in the parent transaction when it deletes the parent Record.

## Indexes and constraints

Use Field shorthands for a single Field:

```yaml
fields:
  - name: email
    label: Email
    type: email
    unique: true
```

Use top-level metadata for composite rules:

```yaml
indexes:
  - name: by-company-status
    fields: [company, status]

constraints:
  - type: unique
    fields: [company, external-id]
```

## Validate before migration

```sh title="Terminal"
dygo entity validate
dygo entity show crm/contact
dygo entity graph crm
```

Validation checks file identity, Field types, links, collections, route conflicts, and Hook conventions before PostgreSQL changes.

## Field types

Attachment creation has [known Studio limitations](/reference/status/#known-limitations-in-the-audited-baseline), particularly for required attachments and Single Entities.

The current storage-backed types are `text`, `email`, `phone`, `password`, `secret`, `long-text`, `int`, `bigint`, `decimal`, `currency`, `boolean`, `date`, `datetime`, `time`, `select`, `link`, `attachment`, and `json`. `collection` represents parent-owned child arrays.

Passwords are hashed and write-only. Secrets are encrypted and write-only; they require [Record encryption keys](/run/secrets/#record-encryption-keys). Neither type may be used as a normal filter, sort, index, or naming Field. App-defined Field types in YAML are not supported.

## Single, private, and system Entities

`is-single: true` defines one framework-owned settings Record. Migration seeds it; Studio opens its form directly. Required stored Fields need non-null defaults. A Single Entity cannot define its own naming strategy or serve as a Link/collection target.

`is-private: true` with `private-owner-field` defines owner-scoped App state. The owner Field must be a Link. Private Entities stay out of generic metadata and Record routes; use `Records.AsPrivate(actor, reason)` in trusted services.

`is-system: true` makes an Entity read-only through ordinary CRUD, Studio, Fixtures, and imports, including Administrator and `AsSystem` calls. App code uses its scoped `Records.System(reason)` writer or a post-sync system Record Patch. See [App SDK](/reference/sdk/).

## Tree Entities

```yaml title="department.entity.yml"
label: Department
name:
  strategy: random
tree:
  parent-field: parent
  label-field: title
fields:
  - name: title
    label: Title
    type: text
  - name: parent
    label: Parent
    type: link
    index: true
    options:
      entity: department
```

The parent must be an optional, indexed Link to the same Entity, with its foreign key enabled. It cannot have a default, fetch rule, or uniqueness rule. A null parent makes a root. Single and collection Entities cannot be Trees.

Self-parenting and cycles are rejected. Move or delete children before deleting their parent. Tree relationships never grant Record permissions. Use normal Record writes to create and move nodes; the [SDK](/reference/sdk/#tree-records) and [HTTP API](/reference/record-api/#tree-queries) provide hierarchy reads.

## Form tabs and layout

Use either top-level `fields` or `tabs`. This layout became available in v0.0.6:

```yaml title="contact.entity.yml layout example"
label: Contact
name:
  strategy: random
tabs:
  - tab: Details
    name: details
    fields:
      - name: full-name
        label: Full Name
        type: text
      - type: column
      - name: email
        label: Email
        type: email
      - type: section
        label: Notes
      - name: notes
        label: Notes
        type: long-text
```

Each tab needs a label, unique kebab-case name, and non-empty Fields. `column` and `section` are layout markers, not database Fields. A section needs a label. Storage Field names stay unique across all tabs; API, constraints, and access rules use those same keys.

For defaults, checks, Link filters, fetch rules, collection conventions, and complete metadata examples, consult the [versioned Entity contract](https://github.com/hapyco/dygo/blob/v0.0.6/docs/entity-metadata.md).
