---
title: Access and permissions
description: Define roles, Entity and Page access, row conditions, and Field restrictions.
---

Dygo enforces permissions on the server. App-owned YAML defines roles and policies. Migration stores effective grants in Core; runtime checks read those Records.

## Define a role

```yaml title="apps/crm/access/_roles.yml"
roles:
  - name: sales-agent
    label: Sales Agent
    description: Works with CRM contacts.
```

Role names are global kebab-case keys. Two Apps cannot define the same role name.

## Grant Entity actions

```yaml title="apps/crm/access/contact.access.yml"
policy:
  - role: sales-agent
    can: [read, create, update, export, print]
```

Base actions are `read`, `create`, `update`, `delete`, `export`, and `print`. `can` also accepts registered [Entity action](/build-apps/actions-and-pages/) names.

Cross-App contributions live at `access/<target-app>/<entity>.access.yml`. Page policies use `access/<page>.page.access.yml`; Page access does not grant Record access.

## Restrict rows and Fields

Policies can add validated row conditions and Field restrictions. For an App that defines an `employee` Link with a `user` Link on its target:

```yaml title="Example Entity policy"
policy:
  - role: employee
    can: [read, update]
    when:
      record.employee.user: actor.user
    fields:
      deny-read: [private-notes]
      deny-write: [status, approved-by]
```

Declare the referenced role and Fields in your App. Dygo compiles the condition into the Record query scope. The same rules apply to lists, direct reads, counts, aggregates, updates, deletes, action locks, and Link searches. Apps do not supply authorization SQL or JavaScript.

Relationship conditions can also use explicit assignment Entities through `in.entity`, `in.value`, and `in.where`. See the [versioned access contract](https://github.com/hapyco/dygo/blob/v0.0.6/docs/access.md) for that shape.

## Validate, apply, and inspect

```sh title="Terminal"
dygo access validate
dygo db migrate --dry-run
dygo db migrate
dygo access show crm/contact
dygo access explain crm/contact --user person@example.com --action read
```

`db migrate` applies access metadata and Fixtures in the migration transaction. `db prepare` creates a missing database and runs the same lifecycle. There is no separate `access apply` command.

`access explain` reports roles, matching policies, row access, and denied Fields. Add `--record 42` to inspect a specific numeric Record ID.

## Assign Users

User-role assignments are runtime data. Manage them through Studio, setup, or explicit environment Fixtures. Defining a role does not assign it to any User. Administrator is a separate User flag.

## Resolve conflicts and export

Duplicate Entity/role policies fail validation unless exactly one contribution uses `override: true`. An override replaces the entire conflicting policy. It does not merge grants, follow App order, or allow override chains.

Export database-authored access into an explicit destination App:

```sh title="Terminal"
dygo access export crm/contact --in crm --dry-run
dygo access export crm/contact --in crm
```

Use `dygo access export --in crm` for roles. Export does not include User-role assignments. Review and validate exported policies before migration.

Removing a role or policy from YAML does not automatically delete the corresponding database Record. Do not treat file deletion as immediate access revocation.

## Trusted App code

Use `Records.AsActor(actor)` for user-scoped SDK operations. Private Entities use owner-scoped `AsPrivate(actor, reason)`. Explicit `AsSystem(reason)` is privileged access for trusted code; it does not permit ordinary writes to system Entities. See [App SDK](/reference/sdk/).
